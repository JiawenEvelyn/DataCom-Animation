# 开发流程

> **这份文档是什么**：一个想法从提出到上线要经过的步骤，以及每一步谁做、产出什么。
> **什么时候用**：开始任何新功能、新课程或较大改动之前。

## 为什么需要流程

前期的做法是「想到一点改一点」：每次反馈后直接改代码。这样改得快，但有三个问题：

1. 没有整体设计，后做的功能经常要推翻先做的（例如报文动画改了三次）。
2. 改动的理由只留在聊天记录里，换一个工作线程就忘了。
3. 没有明确的「完成」标准，很难判断一个功能到底做好了没有。

流程的作用就是把「想清楚」放到「动手」之前，并把决定写下来。

## 角色

| 角色 | 谁 | 职责 |
|---|---|---|
| 产品负责人（Product Owner） | 项目所有者 | 定方向和优先级，评审规格，验收成果；同时是第一个学习者 |
| 开发者（Developer） | Claude | 调研，写规格和设计，实现，测试，维护文档 |
| 评审人（Reviewer） | 项目所有者 | 评审 PR，决定是否合并 |

## 八个步骤

### 1. 需求 → 记入 backlog

任何想法（新功能、改进、bug）先记到 [backlog.md](backlog.md)，写成：

- **用户故事**：「作为学习者，我想要……，这样我就能……」
- **验收标准**：做到什么程度算完成，要能检验（「能看清」不可检验，「每一步停住，点下一步才继续」可以检验）。
- **优先级**：P0 / P1 / P2，对应产品规划书的定义。

这一步**不改代码**。

### 2. 规格 → 写 spec

从 backlog 挑一条开工前，在 [specs/](specs/) 下写一份规格说明，按 [specs/template.md](specs/template.md) 填：目标、范围和非目标、界面草图、数据结构、交互细节、验收标准、测试点、内容来源。

产品负责人评审通过后，spec 状态改为「已确认」，才能开始写代码。这就是 **就绪的定义（Definition of Ready）**：

- [ ] 有 spec，状态为「已确认」
- [ ] 验收标准都可以检验
- [ ] 涉及的知识内容已找到公开来源
- [ ] 产品负责人已确认

课程类的 spec 先写**内容大纲**（这一课讲哪些知识点、用什么场景、报文长什么样、每一步说什么），确认后再做动画。

### 3. 设计决策 → 写 ADR

如果实现中有影响全局的技术选择（例如「课程数据用什么格式」「报文怎么建模」），在 [adr/](adr/) 下写一份架构决策记录：背景、可选方案、决定、后果。小的实现细节不需要 ADR。

### 4. 实现

- 从最新的 main 拉功能分支，分支名用 `feat/…`、`fix/…`、`docs/…`。
- 小步提交，每个提交只做一件事。提交信息第一行说「改了什么」，正文说「为什么」。
- 不在当前 spec 范围外顺手加功能。看到别的问题，记进 backlog。

### 5. 测试

- 运行自动测试：`node tests/smoke.js`（见 [test-plan.md](test-plan.md)）。
- 按 spec 的验收标准逐条手动走查，截图留证。
- 新增的视图和动画要在所有风格、中英文、电脑和手机宽度下检查。

### 6. 评审与合并

- 开 PR，描述里写：对应的 spec 编号、改了什么、测试结果、截图。
- 产品负责人评审。评审意见要么改，要么说明为什么不改。
- 合并到 main，不直接推 main。

### 7. 发布

- 更新在线预览（claude.ai Artifact）。
- 在 [CHANGELOG.md](../CHANGELOG.md) 记一条。
- backlog 里对应条目标记完成。

### 8. 复盘

每个里程碑结束后做一次简短复盘，写在 backlog 末尾的「复盘记录」里：

- 做得好的（继续保持）
- 要改进的（变成新的 backlog 条目或规则）
- 下一个里程碑先做什么

## 完成的定义（Definition of Done）

一个功能满足下面所有条件才算完成：

- [ ] 代码已合并到 main
- [ ] `node tests/smoke.js` 通过，控制台无报错
- [ ] 所有风格、中英文可用；手机宽度可用，无横向滚动
- [ ] 新的讲解条目已登记来源（`SRC` / `SRC_EN`），并有英文版（`KB_EN`）
- [ ] 文档已同步（architecture.md、CLAUDE.md、README 中受影响的部分）
- [ ] CHANGELOG 已记录
- [ ] 产品负责人验收通过

## 中途有新想法怎么办

先进 backlog，按优先级排队。当前里程碑不临时插入新功能，除非：

- 是 bug；或者
- 产品负责人明确要求插队（这时在 backlog 里注明「插队」和原因）。

## 版本号

用 `主版本.次版本.修订号`：

- 次版本 +1：完成一个里程碑（例如 M1 完成 → 0.6.0）。
- 修订号 +1：修 bug 或小改进。
- 主版本 1.0.0：主线课程（M2–M7）全部完成。
